# CivicNeuro SSDLC Audit — FNB AOTY Hackathon

**Audit date:** 24 October 2026

**Scope:** Read-only review of the checked-out resident PWA (“mobile”), organisation dashboard, platform-admin dashboard, Supabase functions/migrations/policies, configuration, tests, and reachable Git history. This is a static workspace audit; deployed Supabase, hosting headers, live RLS/storage state, and external service accounts were not inspected.

## Executive summary

The workspace has useful building blocks: server-side report input limits and rate limits, selected RLS policies, a platform-staff authorization model, an audit trail for report assignment/status changes, email verification UI, private report evidence storage, and a server-side Zego token generator. These do not establish release readiness.

**Do not claim that organisation approval, production Beacon location sharing, complete endpoint authorization, or production deployment hardening is implemented.** The SSDLC document itself was not found. The organization approval UI/functions and most of the listed Edge Function folders are empty. Beacon live sharing remains client-local, and removing/blocking a circle connection does not revoke direct-conversation read access. `npm audit` reported one Critical and one High dependency advisory.

### Endpoint authorization exceptions and gaps

- The `supabase/config.toml` explicitly lists only five functions: `report-submit`, `report-guest-submit`, `report-track` and `snap-and-say` have `verify_jwt = true`; `reprocess-report` has `verify_jwt = false`. The latter checks `x-admin-task-secret` using a constant-time comparison and is staging-host restricted in code.
- `transcribe/index.js` is a success stub with no in-handler authentication or role check and is not explicitly configured in `config.toml`; deployed JWT behavior is therefore not established.
- `report-guest-submit` and `report-track` intentionally support guest flows; they do not prove registered-user RBAC. `report-submit` resolves the reporter from a validated Supabase bearer token.
- `beacon-route` and `zego-token` handlers validate a Supabase user. `zego-token` does not validate that a call target is an accepted/unblocked connection. The Zego handler has no `index.js` deployment entrypoint or Supabase function config in this checkout; only a local development route was found.
- 47 function directories were present; only 8 had non-empty direct files. These 39 folders have no implementation/auth check to inspect: `analytics-query`, `beacon-block-report`, `beacon-connection`, `beacon-search`, `beacon-share-session`, `exports-generate`, `guest-contact-verify`, `invites-accept`, `invites-create`, `job-analytics-precompute`, `job-expire-invites`, `job-expire-location-shares`, `job-guest-contact-purge`, `job-orphan-media-cleanup`, `job-retention-purge`, `job-weekly-digest`, `lifeline-cards`, `lifeline-dispatch`, `media-signed-url`, `media-upload-intent`, `media-validate`, `notifier-send`, `orgs-approve`, `orgs-boundary-upload`, `orgs-register`, `pilot-manage`, `pilot-promote`, `pilot-send-alert`, `platform-second-approval`, `platform-team-invite`, `privacy-delete`, `privacy-export`, `reports-bulk-map-visibility`, `reports-create`, `reports-flag`, `reports-lookup`, `reports-reassign-org`, `reports-update-status` and `whatsapp-webhook`.
- Client-supplied identifiers observed: Beacon request/response/remove/block RPCs accept target/request IDs but bind the action to `auth.uid()`; `staff_reassign_report` accepts `p_report_id` and `p_organization_id` but checks platform staff, target existence and active status. No organization-tenant API implementation was found. No evidence showed the report-submission handler trusting a client-supplied reporter ID.
